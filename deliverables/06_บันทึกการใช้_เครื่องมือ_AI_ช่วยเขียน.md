# 6. บันทึกการใช้เครื่องมือ AI ช่วยเขียน

## Production Control Tower — OEE & Maintenance Operations

> **ชื่อวิชา:** Programming in Automation Systems
> **ชื่อระบบ:** Production Control Tower
> **เครื่องมือ AI ที่ใช้:** AI Pair-Programming (โมเดลภาษาเชิงคำสั่งใน opencode IDE)
> **ระยะเวลา:** กันยายน 2026

---

## 1. บทบาทของ AI (Role of AI)

ผู้ช่วย AI ทำงานในลักษณะ **Autonomous Engineering Partner**
คือทั้งผู้วางสถาปัตยกรรม ผู้เขียนโค้ด ผู้ตรวจสอบคุณภาพ และผู้เขียนเอกสาร
โดยมีหน้าที่หลักดังนี้

1. **วิเคราะห์ข้อกำหนด (Requirements Engineering)**
   อ่านเอกสารส่งงานของโปรเจกต์ต้นแบบ สกัดข้อกำหนดด้านฟังก์ชัน สิทธิ์ตามบทบาท
   และกฎทางธุรกิจ (OEE, workflow ของใบงาน, การจองอะไหล่) ออกมาเป็นโครงสร้างระบบใหม่

2. **ออกแบบระบบ (System Architecture)**
   ออกแบบ ERD, DDL, Foreign Key, RLS Policy, ตารางสิทธิ์สามระดับ
   และเลือกโครงสร้าง Next.js App Router + Supabase PostgreSQL

3. **สร้างโค้ด (Code Generation)**
   เขียนโมดูล Dashboard, เครื่องจักร, ใบงานซ่อมบำรุง, เวลาหยุดเครื่อง, คลังอะไหล่
   รายงาน CSV และบันทึกกิจกรรม พร้อมฟอร์มและ validation ครบทุกหน้า

4. **ตรวจสอบคุณภาพอัตโนมัติ (QA)**
   รัน type-check, lint, unit test และ production build ทุกครั้งที่แก้โค้ด
   และแก้ error จนหมดก่อนส่งมอบ

5. **จัดทำเอกสาร (Documentation)**
   เขียน README, เอกสารส่งมอบ และสร้างภาพหน้าจออัตโนมัติด้วย Playwright

## 2. ลำดับการทำงานร่วมกับ AI (Development Trajectory)

| Phase | งานที่มอบหมายให้ AI | สิ่งที่ได้ | การตรวจสอบโดยมนุษย์ |
|---|---|---|---|
| **Phase 0: วิเคราะห์โจทย์** | อ่านเอกสารต้นฉบับ สรุปข้อกำหนดและขอบเขต | รายการโมดูล 9 โมดูล และสิทธิ์ 3 บทบาท | ตรวจว่าไม่มีข้อกำหนดใดตกหล่น |

| **Phase 2: ตั้งโปรเจกต์** | สร้างโครง Next.js 15 + Tailwind + Supabase Client | `package.json`, `tsconfig`, Tailwind config, ชุดข้อมูลตัวอย่าง | เลือกชุดสีและพื้นฐานระบบดีไซน์ |

| **Phase 5: เชื่อมฐานข้อมูลจริง** | เขียนการ diff snapshot เขียนกลับ PostgreSQL, optimistic update, rollback | `src/lib/supabase/sync.ts`, `plant-context.tsx` | **ตรวจจุดสำคัญ:** UUID ที่เบราว์เซอร์สร้างยังตรงกับแถวที่ฐานข้อมูลได้รับหรือไม่ |
| **Phase 6: ทดสอบและปรับปรุง** | เขียน unit test 37 เคส, type-check, lint, build | `tests/domain.test.ts`, `tests/sync.test.ts` | ผ่าน 37/37, ไม่มี type error, ไม่มี lint warning, build ผ่าน |
| **Phase 7: ส่งมอบ** | เขียนเอกสาร, สร้างภาพหน้าจอ, เตรียม CI | `README.md`, `deliverables/`, `docs/screenshots/`, `.github/workflows/ci.yml` | ตรวจว่าเอกสารตรงกับสิ่งที่ระบบทำจริง |

## 3. วิธีที่ AI ช่วยแก้ปัญหาเชิงวิศวกรรม

### 3.1 ปัญหา: Primary key ของแถวใหม่ไม่ตรงกับที่ฐานข้อมูลบันทึก

**สาเหตุ:** ระบบสร้าง id ด้วย `crypto.randomUUID()` ฝั่งเบราว์เซอร์
แต่โค้ดเขียนกลับฐานข้อมูลตัด primary key ทิ้งก่อนส่ง ทำให้ PostgreSQL สร้าง UUID ใหม่เอง
เมื่อผู้ใช้เปิดใบงานพร้อมผูกอะไหล่ในครั้งเดียว แถวอะไหล่จะอ้าง id ที่ไม่มีอยู่จริง

**วิธีแก้:** เก็บ primary key ไว้เฉพาะตอน insert และตัดออกเฉพาะตอน update
(เพราะตอน update คอลัมน์นี้คือเงื่อนไขใน `where` ไม่ใช่ข้อมูล)
พร้อมเขียนเทสต์ที่ยืนยันว่า id ที่เบราว์เซอร์สร้างถูกส่งไปจริง

### 3.2 ปัญหา: ลำดับการเขียนฐานข้อมูลผิด

**สาเหตุ:** การวนเขียนทีละตารางตามลำดับที่ประกาศไว้ ทำให้ลบแถวแม่ก่อนลบแถวลูก
และเขียนแถวลูกก่อนแถวแม่ ซึ่งจะชน Foreign Key

**วิธีแก้:** แยกการเขียนเป็นสามรอบชัดเจน — ลบก่อน (ลูกก่อนแม่), แล้วเพิ่ม (แม่ก่อนลูก), แล้วอัปเดต

### 3.3 ปัญหา: การย้อนสถานะทับงานที่ผู้ใช้เพิ่งทำ

**สาเหตุ:** ถ้าผู้ใช้แก้ข้อมูลสองครั้งรวดแล้วครั้งแรกล้มเหลว
การย้อนสถานะครั้งแรกจะลบทิ้งการแก้ไขครั้งที่สองไปด้วย

**วิธีแก้:** ให้แต่ละการแก้ไขมีหมายเลขกำเนิด และถอยกลับเฉพาะเมื่อยังเป็นการแก้ไขล่าสุด
รวมถึงจัดคิวการเขียนเรียงกันเป็นลำดับ ไม่ให้สองคำขอซ้อนกัน

### 3.4 ปัญหา: RLS policy อ่านตารางตัวเองจนเกิด infinite recursion

**สาเหตุ:** policy บน `app_users` ต้องเทียบ role ที่ส่งมากับ role ที่เก็บไว้
แต่ถ้า query ตารางเดียวกันใน policy RLS จะบังคับใช้ policy นั้นซ้ำจนวนไม่จบ

**วิธีแก้:** ย้ายการอ่านไปทำใน `security definer` function (`authz.owns_role()`)
ซึ่งอ่านแถวข้อมูลโดยไม่ผ่านการตรวจสิทธิ์ซ้ำ — ยังคงบังคับ policy เพียงครั้งเดียว

### 3.5 ปัญหา: สคริปต์ schema เดิมลบข้อมูลทั้งหมด

**สาเหตุ:** ไฟล์เริ่มต้นด้วย `drop schema public cascade` ซึ่งทำลายข้อมูลจริงทันทีที่รันซ้ำ

**วิธีแก้:** เปลี่ยนเป็นการสร้างแบบเพิ่มเติม (`create table if not exists`) และแยกคำสั่งลบข้อมูลไว้ใน `reset.sql`
พร้อมตรวจ enum ทีละชนิด เพราะการตรวจรวมจะพลาดกรณีที่มี enum บางตัวอยู่แล้ว

### 3.6 ปัญหา: ช่องว่างสิทธิ์ของนักวางแผนงาน

**สาเหตุ:** ฐานข้อมูลกำหนดให้ planner เปิดใบงานได้เฉพาะงานบำรุงป้องกัน
แต่ฟอร์มยังให้เลือกได้ทุกประเภท ผู้ใช้จึงเจอข้อผิดพลาดหลังกดบันทึก

**วิธีแก้:** จำกัดตัวเลือกในฟอร์มให้ตรงกับกฎในฐานข้อมูล
เพราะถึงแม้ฝั่ง client บังคับแล้ว ฐานข้อมูลก็ต้องตรวจซ้ำเสมอ

## 4. ข้อดีและข้อจำกัดของการใช้ AI

### ข้อดี

1. **ลดเวลางานโครงสร้างพื้นฐานได้มาก** — ไฟล์ตั้งต้น, ประกาศชนิดข้อมูล, และโค้ดซ้ำ ๆ ถูกสร้างได้เร็วกว่าเขียนเองมาก
2. **ความปลอดภัยของชนิดข้อมูล** — TypeScript จับความคลาดเคลื่อนได้ก่อนรันจริง
3. **ทบทวนงานตัวเองอัตโนมัติ** — ทุกการแก้โค้ดถูกตรวจด้วย type-check, lint, test และ build
4. **เรียนรู้แนวทางใหม่ระหว่างทำงาน** — เช่น วิธีจัดการ RLS recursion และลำดับการเขียนข้อมูลต่างประเทศ

### ข้อจำกัดและการกำกับดูแลโดยมนุษย์

1. **คนต้องตรวจสอบ (Human-in-the-Loop)** — AI สร้างโค้ดจากความเข้าใจทั่วไป อาจใช้โครงสร้างที่ไม่ตรงบริบาทจริง จึงต้องให้คนตัดสินใจเรื่องสถาปัตยกรรมและกติกาทางธุรกิจ
2. **ตรวจสอบคุณภาพด้วยคำสั่งอัตโนมัติเท่านั้นไม่พอ** — build ผ่านไม่ได้แปลว่า logic ถูกต้อง
   กรณีข้อ 3.1 และ 3.4 ผ่านทุกคำสั่งตรวจ แต่ยังพังเมื่อใช้งานจริง จึงต้องคิดและเขียนเทสต์เพิ่ม
3. **SQL ยังไม่ได้รันกับฐานข้อมูลจริง** — เนื่องจากไม่มีโปรเจกต์ Supabase ในสภาพแวดล้อมนี้
   จึงตรวจได้เฉพาะการอ่านตรรกะ ไม่ได้ยืนยันว่า DDL ทำงานได้จริง ควรรันทดสอบก่อนใช้งานจริง
4. **ภาพหน้าจอยังไม่ได้ตรวจด้วยตา** — สคริปต์สร้างภาพอัตโนมัติทำงานสำเร็จ แต่ควรเปิดดูด้วยตาอย่างน้อยหนึ่งครั้งก่อนส่งอาจารย์

## 5. สรุป

ระบบ Production Control Tower พัฒนาโดยอาศัย AI Pair-Programming เป็นผู้ช่วยวิศวกร
ครอบคลุมตั้งแต่การวิเคราะห์โจทย์ ออกแบบฐานข้อมูล พัฒนาโมดูลทั้งหมด ทดสอบอัตโนมัติ
และจัดทำเอกสารส่งมอบ

จุดที่ AI ช่วยได้มากที่สุดคือการรักษาความสอดคล้องของโค้ดขนาดใหญ่ให้ผ่านการตรวจทุกด้านอัตโนมัติ
และจุดที่จำเป็นต้องใช้คนตัดสินใจคือกติกาทางธุรกิจ สถาปัตยกรรม และการยืนยันผลลัพธ์ก่อนนำไปใช้งานจริง
