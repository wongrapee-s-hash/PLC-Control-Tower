# 8. ข้อจำกัดที่ทราบ และสิ่งที่ยังไม่ได้ตรวจสอบ

เอกสารนี้บันทึกอย่างตรงไปตรงมาว่าอะไร **ผ่านการตรวจสอบแล้ว** และอะไร **ยังไม่ได้ตรวจสอบ**
เพื่อไม่ให้ผู้ประเมินเข้าใจผิดว่าทุกอย่างทำงานจริงครบถ้วน

อัปเดตล่าสุด: หลัง push ขึ้น GitHub และ CI ผ่าน

---

## ส่วนที่ 1 — สิ่งที่ผ่านการตรวจสอบจริง

### 1.1 โค้ดฝั่งแอป

รันคำสั่ง `npm run verify` ได้ผลดังนี้

| การตรวจสอบ | ผลลัพธ์ |
| --- | --- |
| `tsc --noEmit` | ผ่าน ไม่มี type error |
| `eslint .` | ผ่าน ไม่มี warning |
| `npm test` | ผ่าน 37/37 เคส |
| `next build` | ผ่าน 12 routes |

หน้าเว็บทุกหน้าเปิดได้จริงบน `http://localhost:3000` และทดสอบ login ด้วยบัญชีทั้งสามบทบาทแล้ว
ระบบใช้ชุดข้อมูลตัวอย่างที่ตรึงวันที่ `2026-09-30`

### 1.2 ฐานข้อมูล — ผ่านแล้ว ไม่ใช่แค่อ่านโค้ด

`npm run db:test` ยกคอนเทนเนอร์ PostgreSQL 16 ขึ้นมา แล้วรัน
shim → `schema.sql` → `seed.sql` → ชุดทดสอบ RLS 13 ข้อ **ผ่านทั้งหมด**

ตรวจสอบแล้วว่า:

- `schema.sql` และ `seed.sql` รันผ่านโดยไม่มี error
- 11 ตาราง, 25 RLS policy, 15 trigger ถูกสร้างครบ
- ข้อมูลตัวอย่างเข้าครบ 39 แถว activity trail, 10 เครื่อง, 8 ใบงาน, 6 เหตุหยุดเครื่อง
- ทริกเกอร์บันทึก activity ทำงานจริง และใช้รหัสธุรกิจ (`BRG-6205-2RS`) แทน UUID
- **ผู้ใช้ที่ไม่ล็อกอินได้สิทธิ์เท่ากับ `planner`** (fail closed)
- **admin อ่าน audit trail ได้ แต่แก้หรือลบไม่ได้แม้เป็น admin** (append-only)
- engineer เขียน reference data ไม่ได้ แต่เขียนเครื่องจักรได้
- planner แก้เครื่องจักรไม่ได้
- planner เปิดใบงาน PM ได้เฉพาะสถานะ draft/scheduled และเปิดงาน corrective หรือ PM ที่กำลังทำไม่ได้
- ผู้ใช้เลื่อนบทบาทตัวเองเป็น admin ไม่ได้ แต่แก้ชื่อของตัวเองได้
- admin จัดการโปรไฟล์ของคนอื่นได้

**บั๊ก 3 จุดที่เจอจากการรันจริง** (อ่านโค้ดอย่างเดียวไม่พบ — แก้แล้วทั้งหมด)

| # | อาการ | สาเหตุ | แก้ที่ |
| --- | --- | --- | --- |
| 1 | `schema.sql` รันไม่ผ่านตั้งแต่บรรทัดแรก | `authz.current_role()` ถูกสร้างก่อนตาราง `app_users` ที่มัน select อยู่ — PostgreSQL ตรวจ body ของ SQL function ตอนสร้าง | ย้ายบล็อก `authz.*` ไปหลังตาราง |
| 2 | `seed.sql` รันไม่ผ่าน | `tg_op` คืนค่า `INSERT` เป็นตัวพิมพ์ใหญ่ แต่ enum `trail_action` เป็นตัวพิมพ์เล็ก | ครอบด้วย `lower(tg_op)` |
| 3 | `seed.sql` รันไม่ผ่าน | constraint บังคับว่า `reaction <> 'open'` ต้องมี `ended_at` แต่ข้อมูลตัวอย่างมีเหตุที่ "รับทราบแล้วแต่เครื่องยังไม่กลับมาทำงาน" ซึ่งยังไม่จบจริง | เปลี่ยนเป็นบังคับเฉพาะสถานะ `mitigated` / `expired` |

จุดที่ 3 เป็นตัวอย่างว่าทำไมการอ่านโค้ดอย่างเดียวไม่พอ — ข้อมูลตัวอย่างกับ constraint
ขัดกันเอง และตัวไหนผิดขึ้นอยู่กับความหมายทางธุรกิจ ไม่ใช่ไวยากรณ์ SQL

## ส่วนที่ 2 — ยังไม่ได้ตรวจสอบ

### 2.1 ยังไม่เคยรันกับ Supabase จริง

`npm run db:test` ใช้ PostgreSQL 16 ตรง ๆ พร้อม shim ที่จำลอง `auth.users` และ `auth.uid()`
ผลที่ได้จึงครอบคลุม DDL, trigger, view, grant และ RLS — แต่**ยังไม่เคยรันบน Supabase จริง**

สิ่งที่ต่างจาก Supabase จริง:

- Supabase ใช้ PostgREST ซึ่งอ่าน claim จาก JWT ที่ verify แล้ว — shim อ่านค่าจาก session setting
- Supabase มี role และ grant ของตัวเอง ซึ่งอาจทับซ้อนกับที่เราตั้ง
- ไม่ได้ทดสอบ `supabase.auth.admin` สร้างผู้ใช้จริง

**ยังต้องทำ:** สร้าง Supabase project แล้วรัน `schema.sql` → `seed.sql` อีกครั้ง
ถ้า error ให้ส่งข้อความมา แก้ให้

### 2.2 ยังไม่ได้ deploy บน Vercel (push ขึ้น GitHub แล้ว)

| รายการ | สถานะ |
| --- | --- |
| GitHub | **เสร็จแล้ว** — https://github.com/wongrapee-s-hash/PLC-Control-Tower · 6 commits บน `main` |
| GitHub Actions CI | **ผ่าน** — type-check, lint, test 37/37 และ build 12 routes บนเซิร์ฟเวอร์ GitHub |
| Vercel | ยังไม่ได้ deploy มีแค่ build ที่ผ่านในเครื่อง |

การ deploy ต้องมีบัญชี Vercel และการยืนยันตัวตน ซึ่งยังทำแทนไม่ได้
อย่างไรก็ตามตัวโปรเจกต์เตรียมไว้แล้ว — deploy จาก repo ได้ทันทีโดยไม่ต้องตั้งค่าเพิ่ม
(ระบบทำงานในโหมดออฟไลน์จนกว่าจะใส่ env vars ของ Supabase)

### 2.3 ภาพหน้าจอยังไม่ได้เปิดตรวจด้วยตา

สคริปต์ `npm run screenshot` สร้างภาพครบ 14 ภาพใน `docs/screenshots/` และ `deliverables/Screenshots/`
แต่ตอนสร้างภาพ **ยังไม่ได้เปิดด้วยตาว่าภาพถูกต้อง** — เช็กได้แค่ว่าไฟล์ถูกสร้างและมีขนาดสมเหตุสมผล

**ควรตรวจ:** เปิด `deliverables\Screenshots\` ดูสัก 2–3 ภาพว่าไม่มีข้อความล้น, ตารางพัง หรือกราฟไม่ขึ้น

### 2.3.1 สไลด์นำเสนอผ่านการตรวจเลย์เอาต์อัตโนมัติ แต่ยังไม่ได้ดูด้วยตา

`deliverables/Slides/` มีสไลด์ 15 หน้า ทั้ง `.pptx` และ `.pdf`
`npm run slides:check` ตรวจแล้วว่าไม่มีวัตถุล้นขอบสไลด์ และไม่มีข้อความสูงเกินกรอบของตัวเอง
(ข้อความไทยตัดบรรทัดง่ายกว่าอังกฤษ การวัดจริงน่าเชื่อถือกว่าการเดา)

ยังต้องทำ: เปิดดูด้วยตาอีกครั้ง และใส่ชื่อ รหัสนักศึกษา อาจารย์ที่ปรึกษาในหน้าแรก

### 2.4 ยังไม่ได้ทดสอบกับผู้ใช้หลายคนพร้อมกัน

RLS ผ่านการทดสอบกับบทบาททั้งสามแล้ว แต่ยังไม่เคยทดสอบกรณีที่ผู้ใช้สองคนแก้ข้อมูลเดียวกัน
พร้อมกัน ซึ่งเป็นกรณีที่มักมีปัญหาเรื่อง last-write-wins

### 2.5 ยังไม่ได้ดูด้วยตาทุกหน้าในโหมดมืดและขนาดมือถือ

มีการเขียนโหมดมืดและ responsive navigation ไว้ และมีภาพ `12-dashboard-mobile.png`
กับ `14-dashboard-dark.png` แต่ยังไม่ได้ตรวจทุกหน้าในสองโหมดนี้

## ส่วนที่ 3 — ข้อจำกัดของตัวระบบ (ตั้งใจไม่ให้)

### 3.1 ข้อมูลผลผลิตมาจาก MES แต่ยังไม่มีหน้าจอป้อน

ตาราง `production_runs` เก็บผลผลิตรายกะซึ่งปกติต้องมาจากระบบ MES
แต่ระบบนี้ยังไม่มีหน้าจอให้กรอก ผู้ใช้ต้อง import ผ่าน SQL หรือต่อ API ของ MES เอง
ผลกระทบ: ถ้าไม่มีข้อมูลใน `production_runs` ค่า OEE จะคำนวณจากปัจจัยเดียวหรือไม่คำนวณเลย

### 3.2 ยังไม่มีหน้าจัดการผู้ใช้

สิทธิ์ `user.manage` ประกาศไว้ในตารางสิทธิ์แล้ว แต่ยังไม่มีหน้าจอสำหรับเพิ่มหรือแก้ผู้ใช้
ต้องเพิ่มแถวใน `app_users` ผ่าน SQL หรือ Supabase Dashboard เท่านั้น

### 3.3 `demo_principals` เก็บรหัสผ่านแบบข้อความธรรมดา

เหมาะกับการสาธิตเท่านั้น **ต้องลบตารางนี้ทิ้งก่อนขึ้นใช้งานจริง**
RLS ปิดกันการอ่านจาก `anon` ไว้แล้ว แต่ข้อมูลยังอยู่ในฐานข้อมูลจริง

### 3.4 ไม่มีการแจ้งเตือนอัตโนมัติ

จุดสั่งซื้ออะไหล่และงานที่ค้างแสดงเป็นธงบนหน้าจอ แต่ไม่ส่งอีเมลหรือ LINE แจ้งเตือน

### 3.5 เวลาสูญเสียคำนวณจากที่กรอกเอง ไม่ได้อ่านจาก PLC

ระบบบันทึก `started_at` / `ended_at` ของเหตุหยุดเครื่องด้วยมือ
ยังไม่ได้เชื่อมกับสัญญาณ PLC จริงผ่าน Modbus TCP, EtherNet/IP หรือ OPC UA

### 3.6 เวลาที่บันทึกเป็นเวลาไทย ไม่ใช่เวลาจริงของเครื่อง

ระบบตรึงวันที่ไว้ที่ `2026-09-30` เพื่อให้ตัวเลข OEE ไม่เปลี่ยนไปเรื่อย ๆ ซึ่งเหมาะกับการสาธิต
แต่ถ้าเชื่อมฐานข้อมูลจริง ต้องตรวจว่า timezone ของฐานข้อมูลตรงกับ `Asia/Bangkok`

## ส่วนที่ 4 — ความปลอดภัย

### 4.1 ยังมีช่องโหว่ใน dependency ที่แก้ไม่ได้โดยไม่อัปเกรด Next.js ใหญ่

`npm audit` เหลือ 2 รายการ ทั้งหมดอยู่ใน dependency ที่ Next.js ดึงมาเอง ไม่ใช่โค้ดเรา

| แพ็กเกจ | ปัญหา | แก้ได้โดย |
| --- | --- | --- |
| `next` → `postcss` | XSS จาก CSS stringify | ต้องอัปเกรดเป็น Next.js 16 (เปลี่ยนใหญ่) |
| `next` → `sharp` | ช่องโหว่ของ libvips | ต้องอัปเกรดเป็น Next.js 16 |

สิ่งที่ปิดไปแล้ว: `supabase-js` (auth-js path traversal), `eslint`, `tsx`/`esbuild`, `playwright`, `postcss` ตัวที่เราใช้เอง

**ความเสี่ยงจริงต่ำ** เพราะ postcss ทำงานตอน build ไม่ได้ทำงานตอนผู้ใช้เข้าเว็บ แต่ควรอัปเกรด Next.js เมื่อมีเวลา

### 4.2 เขียนแบบ optimistic แต่ไม่มี transaction

ถ้า PostgreSQL ปฏิเสธบางแถว การเขียนแต่ละคำสั่งที่ผ่านไปแล้วจะไม่ถูกย้อนกลับ
ระบบย้อนสถานะ**บนหน้าจอ** ให้ตรงกับฐานข้อมูล แต่ข้อมูลจริงอาจเหลือเป็นบางส่วน
การแก้จริงต้องใช้ RPC function ที่ครอบด้วย transaction เดียว

### 4.3 เขียนวันที่เป็น UTC แต่แสดงเป็นเวลาไทย

ถ้าเซิร์ฟเวอร์และฐานข้อมูลอยู่คนละโซนเวลา ค่าที่แสดงอาจคลาด 1 ชั่วโมง
ควรทดสอบเมื่อเชื่อมจริง

### 4.4 ไม่มี rate limiting ที่ฝั่งแอป

หน้าเข้าสู่ระบบไม่มีการล็อกบัญชีหลังล้มเหลวซ้ำ
ถ้าใช้ Supabase Auth จริง ต้องดูว่า Supabase เปิด rate limiting ให้แล้วหรือยัง
