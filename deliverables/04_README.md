# Production Control Tower

ระบบศูนย์ควบคุมการผลิตสำหรับโรงงานอิเล็กทรอนิกส์แบบสายการผลิต (discrete manufacturing)
ครอบคลุมตั้งแต่ทะเบียนเครื่องจักร ใบงานซ่อมบำรุง เวลาหยุดเครื่อง คลังอะไหล่ และรายงาน OEE
ในหน้าจอเดียว

> ระบบนี้รันได้ทันทีโดยไม่ต้องตั้งค่าฐานข้อมูล — คัดลอก repo แล้ว `npm install && npm run dev`
> แล้วเข้าสู่ระบบด้วยบัญชีสาธิตได้เลย เมื่อต้องการใช้งานจริงให้เชื่อม Supabase ตาม
> [การเชื่อมต่อฐานข้อมูล](#การเชื่อมต่อฐานข้อมูล)

## ความสามารถของระบบ

| หน้า | ความสามารถ |
| --- | --- |
| `/dashboard` | OEE รวมและรายสาย, แผนภาพ availability, สาเหตุหยุดเครื่อง, งานค้าง, สินค้าขาด |
| `/assets` | ทะเบียนเครื่องจักรพร้อมตัวกรอง, เพิ่ม/แก้ไขสเปก, เปลี่ยนสถานะการผลิต |
| `/assets/[id]` | ประวัติเครื่อง, ผลงานกะ, OEE เทียบเป้า, ใบงานและเหตุการณ์ที่เกี่ยวข้อง |
| `/work-orders` | คิวงานซ่อมบำรุงพร้อมตัวกรองตามสถานะ/ความเร่งด่วน, เปิดใบงานใหม่ |
| `/work-orders/[id]` | เดินสถานะตาม workflow, จอง/เบิกอะไหล่, บันทึกแรงงานและเวลาสูญเสีย, ผูกเหตุหยุดเครื่อง |
| `/downtime` | บันทึกเหตุหยุดเครื่องตามสาเหตุ, ปิดเหตุการณ์, แจกแจงสาเหตุ |
| `/parts` | คลังอะไหล่, จุดสั่งซื้อ, ยอดที่ต้องสั่งซื้อ, ปรับยอดคงคลัง |
| `/reports` | ส่งออก CSV 5 ชุด (ใบงาน, เครื่องจักร, เวลาหยุด, อะไหล่, ผลผลิตรายกะ) |
| `/activity` | บันทึกกิจกรรมแบบ append-only ที่เขียนโดย trigger ในฐานข้อมูล |

## การเชื่อมต่อฐานข้อมูล

### 1. สร้าง schema

เปิด Supabase Dashboard → SQL Editor แล้วรันไฟล์ตามลำดับ

| ไฟล์ | หน้าที่ |
| --- | --- |
| `supabase/schema.sql` | ตาราง, enum, trigger, view, RLS, grant — **เพิ่มเติมเท่านั้น รันซ้ำได้** |
| `supabase/seed.sql` | ข้อมูลตัวอย่างชุดเดียวกับที่แอปใช้ตอนออฟไลน์ |
| `supabase/reset.sql` | **ลบข้อมูลทั้งหมด** ใช้เมื่อต้องการเริ่มใหม่เท่านั้น |

`schema.sql` ไม่มี `drop schema` จึงปลอดภัยกับโปรเจกต์ที่มีข้อมูลอยู่แล้ว
ถ้าจะใช้กับโปรเจกต์จริง ให้ลบตาราง `demo_principals` ทิ้ง เพราะตารางนั้นเก็บรหัสผ่านแบบข้อความธรรมดา

### 2. สร้างผู้ใช้

สร้าง user ใน Supabase Auth (Authentication → Users) แล้วใส่แถวใน `app_users` ให้ตรงกับ `user_id`

```sql
insert into public.app_users (user_id, email, display_name, role, site_code)
values (
  '<user_id จาก Authentication>',
  'your@email.com',
  'ชื่อที่แสดง',
  'engineer',           -- admin | engineer | planner
  'SMT-01'
);
```

หากไม่มีแถวนี้ ระบบจะไม่ยอมให้เข้าใช้งาน เพราะ RLS อ่านสิทธิ์จากตารางนี้ทั้งหมด

### 3. ตั้งค่า environment

คัดลอก `.env.example` เป็น `.env.local` แล้วใส่ค่าจาก Project Settings → API

```bash
NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon key>
```

เมื่อตั้งค่าแล้ว ระบบจะสลับจากโหมดออฟไลน์เป็นโหมดจริงโดยอัตโนมัติ
(ป้ายสถานะบนแถบด้านบนจะเปลี่ยนจากสีส้มเป็นเขียว) และทุกการแก้ไขจะถูกเขียนกลับ PostgreSQL
ถ้าฐานข้อมูลปฏิเสธ ระบบจะย้อนสถานะกลับและแสดงเหตุผลด้านบน

## โครงสร้างโปรเจกต์

```
src/
├─ app/
│  ├─ (console)/          ← ทุกหน้าที่ต้องเข้าสู่ระบบ (AppShell ตรวจสิทธิ์ให้)
│  ├─ login/              ← หน้าเข้าสู่ระบบ
│  └─ layout.tsx          ← provider chain: Theme → Auth → Plant
├─ components/            ← UI แยกตามโดเมน (dashboard, assets, parts, ...)
├─ context/
│  ├─ auth-context.tsx    ← session + can() (Supabase Auth หรือ demo)
│  └─ plant-context.tsx   ← snapshot เดียวของทั้งระบบ + การ persist
├─ data/
│  ├─ demo-dataset.ts     ← ข้อมูลตัวอย่างที่ตรึงวันที่
│  ├─ plant-store.ts      ← pure mutations ทั้งหมด (ไม่มี side effect)
│  └─ selectors.ts        ← derived data ทุกหน้าใช้ร่วมกัน
├─ lib/
│  ├─ oee.ts              ← สูตร OEE, MTTR, PM compliance
│  ├─ inventory.ts        ← สต็อก, การจอง, การขาด
│  ├─ workflow.ts         ← ตารางการเคลื่อนสถานะ
│  ├─ permissions.ts      ← ตารางสิทธิ์ตามบทบาท
│  └─ supabase/           ← client + การ diff snapshot ไปเขียน DB
└─ types/domain.ts        ← union ทุกตัวที่ไปถึงฐานข้อมูล
supabase/                  ← schema.sql, seed.sql, reset.sql
tests/domain.test.ts      ← unit tests ของ domain layer
```

**หลักการสำคัญ** — `plant-store.ts` เป็น pure function ทั้งหมด
รับ snapshot เข้า คืน snapshot ใหม่ ไม่แตะ DOM, ไม่แตะฐานข้อมูล
ทำให้ทดสอบได้โดยไม่ต้องมีระบบอื่น และผู้เรียนอ่านโค้ดเห็นกฎทางธุรกิจทั้งหมดอยู่ที่เดียว

## การคำนวณ OEE

```
OEE = ความพร้อมเครื่อง × ประสิทธิภาพ × คุณภาพ
```

| ตัวประกอบ | สูตร |
| --- | --- |
| Availability | นาทีที่เครื่องทำงาน ÷ นาทีตามแผน |
| Performance | ชิ้นที่ผลิต ÷ (นาทีตามแผน × 60 ÷ takt) จำกัดไม่เกิน 100 |
| Quality | ชิ้นดี ÷ (ชิ้นดี + ชิ้นเสีย) |

ถ้าไม่ได้กำหนด takt ระบบจะตั้ง Performance = 100 และคำนวณจากสองปัจจัยแรกเท่านั้น
ค่าที่ได้ถูกจำกัดไว้ที่ 0–100 เสมอ และรองรับกรณีไม่มีข้อมูลกะเลยโดยไม่เกิดการหารด้วยศูนย์

## กฎการเคลื่อนสถานะใบงาน

```
ร่าง ──→ ตั้งกำหนด ──→ กำลังทำ ──→ เสร็จ ──→ ตรวจรับ
  │           │            │  ↑              │        │
  │           │            └──┤ ขาดอะไหล่ ──┘        │
  └───────────┴───────────────┴──→ ยกเลิก           │
                                       ↑             │
                                       └── กลับมาแก้ ──┘
```

- ข้ามสถานะไม่ได้ เช่น ร่าง → เสร็จ ใช้ไม่ได้
- ปิดงานไม่ได้ถ้ายังมีอะไหล่ที่จองแล้วแต่ยังไม่ครบ
- เปลี่ยนสถานะเครื่องเป็น "กำลังผลิต" ไม่ได้ถ้าเครื่องนั้นมีงานที่กำลังทำอยู่
- ลบใบงานได้เฉพาะร่างที่ยังไม่เริ่ม — ประวัติที่เริ่มไปแล้วห้ามลบ

ตารางนี้มีสองชั้น: `src/lib/workflow.ts` ตรวจก่อนเพื่ออธิบายให้ผู้ใช้ และ trigger
`work_order_transition_allowed()` ในฐานข้อมูลตรวจซ้ำเพื่อไม่ให้ client ที่ค้างอยู่ทำลายข้อมูล

## ข้อจำกัดที่ทราบ

- **ข้อมูลผลิตภาพมาจาก MES** — หน้า `/reports` อ่าน `production_runs` แต่ยังไม่มีหน้าจอสำหรับ
  ป้อนข้อมูลกะ ผู้ใช้ต้อง import ผ่าน SQL หรือเชื่อม API ของ MES ก่อน
- **ผู้ใช้ต้องสร้างเอง** — ยังไม่มีหน้าจัดการผู้ใช้ (`user.manage`) แม้สิทธิ์นี้จะอยู่ในตารางแล้ว
- **`demo_principals` เก็บรหัสผ่านแบบข้อความธรรมดา** — เหมาะกับการสาธิตเท่านั้น
  ต้องลบทิ้งเมื่อนำขึ้นใช้งานจริง
- **ไม่มีการแจ้งเตือนอัตโนมัติ** — จุดสั่งซื้อและงานที่ค้างแสดงเป็นธงบนหน้าจอ แต่ยังไม่ส่งอีเมลหรือ LINE
- **เวลาสูญเสียคำนวณจากนาทีที่กรอกเอง** — ยังไม่ได้เชื่อมกับ PLC signal จริง
